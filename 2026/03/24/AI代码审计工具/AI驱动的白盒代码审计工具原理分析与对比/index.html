    AI驱动的白盒代码审计工具原理分析与对比

    Posted on 2026-03-24 Word count in article: 5.1k Reading time ≈ 5 mins.

    静态分析引擎 + LLM

    AST&&CFG&&DFG

    维度 AST（抽象语法树） CFG（控制流图） DFG（数据流图）
    核心关注 代码的语法结构（静态） 代码的执行路径（动态） 数据的依赖关系（数据流向）
    基本单元 语法节点（赋值、运算、判断） 基本块（连续执行的代码段） 数据节点（变量、常量、运算）
    连接方式 父子节点（语法层级） 有向边（执行跳转） 有向边（数据依赖）
    典型问题 “这段代码有哪些语法错误？” “这段代码有哪些执行路径？” “变量 y 的值来自哪里？”
    应用场景 代码解析、语法检查、代码格式化 代码优化、覆盖率测试、死代码检测 常量传播、污点分析、并行计算

    污点分析（Taint Analysis）

    污点分析是一种基于 DFG（数据流图）的静态程序分析技术，核心目标是：
    追踪程序中 “受污染的数据”（比如用户输入、外部接口传入的数据）从源头（Source） 出发，经过哪些路径传递，最终是否到达危险点（Sink）；若传递过程中没有经过净化函数（Sanitizer） 处理，就可能存在安全漏洞（比如 SQL 注入、XSS、命令注入）。

    组件 含义 例子
    Source（源头） 产生 “污点数据” 的位置（不受信任的输入） 用户输入（input()/request.POST）、文件读取、网络请求返回值
    Sanitizer（净化器） 清洗 / 验证污点数据的函数（能把 “污点” 变成 “干净数据”） SQL 转义函数（mysql.escape_string()）、XSS 过滤函数（html.escape()）
    Sink（危险点） 执行敏感操作的位置（若传入未净化的污点数据，会触发漏洞） SQL 执行（cursor.execute()）、系统命令调用（os.system()）、页面输出

    模式匹配

    模式匹配是一种“按模板找目标” 的技术 —— 你先定义一个 “模式（模板）”，然后在目标数据（比如代码 AST/DFG、字符串、列表）中，找出和这个模板结构 / 内容匹配的部分，甚至可以提取匹配到的关键信息。

    • 结合AST：定位危险代码
      • 例如未净化的SQL拼接：
    • 结合DFG：定位数据流向模式：
      • 例如想找”用户输入->未净化->SQL执行“的数据流模式

    LLM后处理

    • LLM 后处理的核心逻辑：静态分析做 “基础筛选”（找可疑模式 / 路径），LLM 做 “智能精加工”（上下文推理 + 误判修正 + 排序 + 格式化），最终提升分析结果的准确率和可用性；
    • LLM 的核心价值：弥补静态分析 “无上下文理解、无常识推理、仅机械匹配” 的短板，利用预训练的知识储备和推理能力，处理静态分析规则无法覆盖的场景；

    RAG + 代码知识库

    核心思路：不依赖定义原则，而是构建一个代码安全知识库，让LLM通过检索相似模式来做判断

    RAG（Retrieval Augmented Generation）

    RAG = 先检索，再生成

    差异对比

    维度 静态分析引擎 + LLM RAG + 代码知识库
    LLM 的知识来源 仅预训练通用知识 预训练知识 + 实时检索的漏洞知识库
    LLM 在流程中的角色 事后 “精加工”（修正 / 排序 / 格式化） 全程 “精准判断”（结合案例做推理）
    是否依赖外部知识库 否 是（核心依赖）
    对于已知漏洞的检验能力（CWE Top 25） 强，无规则则无检测 中，可泛化相似模式
    对于未知/新型漏洞的检验能力 弱，无规则则无检测 中，可通过案例学习
    业务逻辑漏洞 极弱，难以用规则描述 中，可通过案例学习
    误报率 高（原始）→ 中（LLM过滤后） 中（取决于检索精度）
    漏报率 中（规则覆盖决定） 中高（知识库盲区）
    速度
    		 快（静态分析本身很快，LLM是瓶颈） 慢（检索+LLM双重开销）
    可解释性/可审计性
    		 高，规则可追溯 低，LLM判断难以追溯

    guardian-cli-测试实践（二）

    Posted on 2026-04-08 Word count in article: 60k Reading time ≈ 55 mins.

    针对 DeRPnStiNK 靶场特定策略改进

    针对上述问题做以下尝试：优化系统提示词，增强工具定义的“描述元数据”

    优化系统提示词

    分析位于/ai/prompt_templates下的panner.py以及tool_selector.py

    1. Planner：它的提示词太宏观了（”Think strategically”, “Follow frameworks”），它把“目录扫描”看作一个任务节点，做完了就认为任务结束，缺乏特征触发的微观逻辑。
    2. Tool Selector：它只知道工具的定义（gobuster 是扫目录的，wpscan 是扫 WP 的），但不知道“当 gobuster 扫到 /wp- 时，必须调用 wpscan这种因果逻辑。
      针对这两个问题，尝试进行以下优化：
    • 修改 PLANNER_SYSTEM_PROMPT：赋予Planner“递归思维”以及“特征敏感度”
    • TOOL_SELECTOR_SYSTEM_PROMPT，在工具选择器里植入工具之间的依赖规则。
    • 微调 PLANNER_DECISION_PROMPT：在每次做决策时，强制 AI 检查“上下文”中是否包含需要递归的特征。

    Result

    分析修改prompt之后的决策，是这是一个非常典型的AI 流程编排器在遇到工具静默失败时的逻辑困境：
    Planner 在最后阶段做出的决策，本质上是一个基于幻觉的推测：

    • 它看到了什么（事实）：
      • WhatWeb 确认了技术栈（Apache/Ubuntu）
      • Gobuster 发现了 /weblog/ 目录（线索）
      • SQLMap 报告“未找到参数”（明确的失败）
      • WPScan 数据缺失（空字符串或错误）。
    • 它做了什么推断：
      • 关联：它看到 /weblog/ 和 wordpress_audit_workflow，判断这是一个 WordPress 站点（基于prompt的修改）
      • 建议重试：它建议“Re-run wpscan with increased verbosity…”。
      • 逻辑漏洞：Planner 并没有意识到 WPScan 其实已经运行过了（且崩溃了 Exit Code 4）。它以为 WPScan 还没跑，或者跑得太浅。
    • 存在的问题：
      • 中间件逻辑缺失：在 Gobuster 和 WPScan 之间，应该有一个“结果解析器”。这个解析器应该从 Gobuster 的输出中提取出 http://derpnstink.local/weblog/，并生成一个新的任务队列。
      • Planner 的短视：Planner 的提示词（Prompt）可能设计为“如果发现 WordPress，扫描根目录”。它并没有逻辑去“遍历所有 Gobuster 发现的子目录并逐个扫描”。
      • 数据未注入：Gobuster 的结果仅仅被 Analyst 当作“情报（Findings）”打印了出来，而没有被注入到 Planner 的“待办任务流（Workflow Stream）”中。
        即修改prompt让AI具备关联不同工具扫描结果的意识，但是这些工具之间传输信息的数据通道不够完整，他们需要将运行工具输出的结果，不管是实际输出或者是报错输出都应该存储进记忆体，让AI分析，让数据流通。
        这里其实猜测数据传输存在一定问题，可能字段丢失，可能解析存在问题等……排除是模型无法根据信息关联下一步的可能性
    增强工具定义的“描述元数据”

    .yaml：命令行输入 guardian run --workflow wordpress_audit.yaml->加载：Python 程序（Guardian 的核心）首先读取这个 YAML 文件->解析：Python 使用 yaml 库（如 pyyaml）把这个文本文件转换成 Python 能懂的字典或对象->程序把这些信息准备好，准备喂给 AI

    .yaml文件的description字段，能够作为Guardian-CLI 发给 AI 的任务清单，指导它的动作，作为系统提示词的一部分
    以及dependencies字段，能够作为告诉AI的不同工具的顺序依赖关系
    但是这是理想的状态下，但是尝试了改description和prompt都发现解决不了根本问题，所以后续去看源码发现，workflow工作模式本身设定的逻辑仅仅只是使用工具扫描然后将使用的工具和扫描结果发给planner aegnt调用ai LLM输出报告。真正让ai参与过程决策的是autonomous这个专用workflow。

    Source Code Analysis

    workflow.py: _load_workflow


    他读取了YAML文件，读取了steps字段。并且他在这里将steps这个列表传给了run_workflow 方法，然后按顺序执行 self._execute_step(step)。
    返回值：一个列表，列表中的每一项都是一个字典，代表工作流中的一个具体步骤

    core/workflow.py: run_workflow

    ![[Pasted image 20260408231605.png]]

    重点在于：


    这个函数地作用仅仅只是：整理工具所发现的漏洞，整理执行工具的信息，然后通过构建的prompt

    调用大模型接口生成对应的结果报告
    因此，这部分调用planner agent的思考仅仅只是作为事后复盘的思考，对于已经搜集到的信息做一个判断，而不是通过agent思考，得出了某个信息，下一步应该怎么深入进行一个实时的决策（eg：发现3306端口，分析对应有mysql）

    core/workflow.py

    与之对应的是另一个单独的工作模式，从后面的分析来看，是这个独有的模式才是AI参与过程中决策而不是仅仅作为对工具扫描结果的分析

    这里的主执行循环能看见AI的决策参与在过程中：

    • 循环条件：当前步数 current_step 未达到最大步数 max_steps（这个数值位于autonomous.yaml）
    • 决策：在每次循环中，都调用 self.planner.decide_next_action()，让规划智能体分析当前状态并决定下一步行动。
    tool_agent.py

    存在两种模式：

    • AI 决策模式

    在这个模式下，ToolAgent 会询问 AI，AI 会返回一个工具名和一串命令参数字符串（例如 "-sV -sC"）

    • 直接执行模式

      这个方法接收 **kwargs，并直接传递给 tool.execute()，对应的是workflow调用工具的方法

    Conclusion

    • 通过查看源码发现，这个工具是不能通过定义workflow的方式来进行真正智能化的渗透测试扫描，因为他的代码逻辑当中AI并没有参与运行时决策。它不能实时做出决策的根本原因在于作者可能也许是想写定义不同的工作流以适应不同场景下的渗透测试，但是实际上工具是按照workflow定义的串行运行，再将得到的扫描信息传给AI分析可能的漏洞。
    • 后续应该考虑从autonomous下手考虑怎么实现真正的AI驱动的黑盒扫描
